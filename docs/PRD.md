# Lynx 初版产品需求文档

日期：2026-11-24；工程状态更新：2026-11-25。状态：一期功能已实现，分项验收见第 13 节。

本文的“已确认”表示产品要求已确定，不表示功能已完成。“建议”用于辅助后续技术决策；“待确认”不能作为已批准的实现约束。当前已有原生四页、行情与计算、后台刷新、菜单栏、通知、本地保存及 Agent 入口；已完成离线测试及美股实连，系统交互和客户端验收限制见第 13 节。

## 1. 产品定位与目标（已确认）

Lynx（猞猁）是面向其他投资者的独立、本地 Mac App，帮助用户在港股和美股中查看 CSP（现金担保卖出看跌期权）及 CC（备兑卖出看涨期权）的模拟机会，理解候选合约及排序原因。

- 支持 Apple Silicon M1 及以后，不支持 Intel。
- 首期券商为富途 / moomoo，通过用户自装的官方 OpenD 获取行情。
- 不依赖开发者服务器，不做云同步。
- 券商接入为 App 内部插件，首期随 App 提供；不是其他软件的插件，也不做插件商店。
- 技术栈为全 Swift：SwiftUI 界面，Swift 策略计算与券商接入。不引入 Python 运行时或 Python 子进程，也不随包打包 Python；用户无需安装 Python 开发环境。
- 仓库公开，项目采用 MIT 许可证，见 [LICENSE](../LICENSE)。
- 一期包含 AI 集成：支持为 Codex 和 Claude Code 安装 Lynx 技能，安装后通过 Agent 操作和配置本地 App；第 3.1 节标记的一期能力已获确认；临时查询与 MCP 不在本期。

## 2. 范围与模拟边界（已确认）

首期只做行情和模拟分析，不读取真实现金、持仓、账本，不选择或读取交易账户，不下单、撤单或执行交易。连接 OpenD 与检查行情权限即可，不以真实账户查询作为使用前置条件。

所有计算按一手期权模拟，使用真实合约乘数；不能假定所有合约乘数均为 100。所需字段缺失时沿用适用的数据缺失语义，不能凭空补乘数或把未知当零。

| 方向 | 用户输入 | 模拟含义 | 结果边界 |
| --- | --- | --- | --- |
| CSP | 愿意接货的最高价 | 模拟卖出一手看跌期权，展示所需担保现金 | 不证明用户有足够现金 |
| CC | 不输入持仓成本；按该方向配置筛选参数 | 假设已有足够股票覆盖一手期权，以当前股价对应的一手股票市值为收益率基数 | 不证明用户真实持股，不计算真实持仓总回报 |

输入币种随标的。结果明确标注“模拟”；每手净权利金、担保现金等按对应合约规模计算，不把一手期权简单等同于 100 股。

首期不做真实组合容量评估、真实集中度管理、券商登录凭据托管、OpenD 安装或进程代管。

## 3. 用户流程与设置（已确认）

1. 用户自行安装、登录并保持官方 OpenD 可用。Lynx 提供引导、连接状态及行情权限检查，默认连接本机，端口可调。
2. 用户添加关注股票，按股票分别打开 CSP、CC，可同时开启两个方向。
3. CSP 填愿意接货的最高价；CC 不接入、填写或保存持仓成本。缺少某方向其他必填项时，仅该方向显示“待设置”，不阻塞另一方向或其他股票；CC 不因缺少成本而待设置。
4. 期限等高级策略参数采用适用的 OM 默认值，默认收起；用户可展开修改并恢复默认。已核实默认值详见[规则与数据口径](STRATEGY.md)。
5. 用户手动刷新，或选择定时刷新；按“美股或港股 → CSP 或 CC → 股票列表”查看结果。
6. 展开某只股票，查看其他所有合格期限、行权价合约和该股票内部的排序。无合格结果或未入选时，可以查看对应原因。

费用不属于用户可修改的高级设置，相关来源见第 8 节。

### 3.1 AI 集成（一期范围已确认）

目标：用户安装 Lynx 提供的智能体技能后，可以在 Codex 或 Claude Code 中用自然语言查看、操作和配置 App。此处 Claude 按 Claude Code 理解；本期不承诺 Claude 网页版或其他客户端接入。交互参考 Surge 的 AI 集成页面，不代表沿用其内部实现或已验证 Lynx 的接入能力。

**安装与管理流程**

1. 用户进入 Lynx 的“AI 集成”页面，查看 Agent 可执行的操作及 Codex、Claude Code 两张独立安装卡片。
2. 每张卡片显示对应客户端的检测结果及 Lynx 技能安装状态，并提供安装、更新（需要时）和卸载入口。未检测到客户端时提供说明，不把技能安装等同于安装 Agent 客户端。

用户自行安装和登录所用 Agent；Lynx 不代管 Codex / Claude Code 账户、订阅或模型密钥。不要求启用 AI 集成才能使用其他一期功能。

不纳入一期的 OM 能力包括真实现金与组合查询、持仓 / 账本 / 交易记录、真实业绩、基于持仓的平仓和移仓建议、Wheel 生命周期、账户增删、外部消息渠道、自有 Bot、服务器定时任务与服务管理、源码浏览及版本发布。单合约查询和推荐仍遵守本 PRD 的 CC 现价市值收益率基数、CSP 担保现金和无集中度规则，不能把能力对齐解释为取消这些差异。

入选的 Agent 修改能力与界面操作使用同一套设置校验和业务规则，仅在用户明确授权范围内执行。本期使用共同校验和结果读回，不提供独立配置预览工具。修改成功后自动保存并同步反映到 App。返回实际结果与生效值；输入无效、App 不可用或操作失败时明确报告，不能把请求已发送当作设置已生效。通知权限等系统授权仍由正常系统流程完成，未获授权时应如实显示。

AI 集成沿用行情与模拟边界：不能读取真实现金、持仓或账本，不能交易、修改费用或代管 OpenD。Agent 读取到的内容由用户所选 Agent 客户端按其数据处理方式使用；Lynx 本身不新增开发者服务器或云同步。

## 4. 计算、筛选与排序（已确认规则）

### 4.1 与 OM 的关系

OM 指用于参照策略规则的 options monitor。Lynx 复用其适用计算规则、门槛和缺失语义，但有明确差异，不能宣称完全没有策略差异：

- 去掉基于真实账户容量的资格判断。
- 去掉跨标的排序中的集中度因素。
- CC 不接入或填写持仓成本；移除依赖成本的筛选门槛，不将缺失成本当零。收益率基数使用当前股价对应的一手股票市值，具体公式见第 4.2 节。
- 输出为一手期权分析结果，不作账户可交易性保证。

除上述差异外，其余适用门槛及缺失语义保留。未知值不能当零；已知持仓、现金或账户容量不是任何模拟方向的前置数据。固定参照、实际门槛、公式、默认值、精度和已知覆盖边界见[规则与数据口径](STRATEGY.md)；不能据固定测试宣称 OM 所有策略均已兼容。

### 4.2 先按持有期收益分档

| 方向 | 用于分档的收益口径 |
| --- | --- |
| CSP | 持有期净收益率 |
| CC | 持有期净权利金收益率 |

CC 收益率口径已确认：

- `收益率基数 = 当前股价 × 一手期权对应的真实股数`。股数依据合约真实乘数及一手规模确定，不固定为 100。
- `持有期净权利金收益率 = 每手净权利金 ÷ 收益率基数`。净权利金使用第 8 节统一费用模型，不计入股票价格涨跌形成的盈亏。
- 年化收益率在同一基数的持有期净权利金收益率上换算；具体年化天数与换算规则仍按适用 OM 规则核验，不另设成本口径。年化用于展示，不主导排序。
- 基数与净权利金使用同一轮结果采用的行情及其时间；历史参考结果明确显示数据时间，不将旧股价称为实时股价。
- 股价或合约规模缺失、无效时，收益率标为不可计算，不以零、假定乘数或历史成本代替，也不作为有效收益率参与分档。

例如当前股价为 50、该合约一手对应 200 股、每手净权利金为 200，则基数为 10,000，持有期净权利金收益率为 2%。这是净权利金相对现价市值的比例，不是持仓总回报。

先按相应持有期收益率从高到低，以 `0.002`（即 **0.2 个百分点**）分档。每档以该档最高收益率为锚，不能用相邻候选的差距进行链式合并。较高收益档在前，再按档内规则比较；年化收益率不主导排序。

例如收益率为 10.00%、9.85%、9.70% 时，前两项距最高值不足 0.2 个百分点，可以同档；第三项距 10.00% 为 0.3 个百分点，不能因它与 9.85% 相邻且差距较小而并入同档。阈值恰好相等的边界与精度处理需随 OM 对照核验。

### 4.3 档内排序优先级

以下按从左到右依次比较，前项相同再比较后项。价差使用适用 OM 口径；OI 为未平仓量，未知 OI 不转成零，也不被视为已知值。

| 比较范围 | 方向 | 档内优先级 |
| --- | --- | --- |
| 同一股票的合约 | CSP | 接货折价大 → 价差小 → OI 已知且高 → 净权利金高 → 稳定 ID |
| 同一股票的合约 | CC | 行权价高 → 价差小 → OI 已知且高 → 净权利金高 → 稳定 ID |
| 不同股票的代表合约 | CSP | 接货折价大 → 价差小 → OI 已知且高 → 净权利金高 → 稳定 ID；不含集中度 |
| 不同股票的代表合约 | CC | 行权价高于现价的百分比大 → 价差小 → OI 已知且高 → 净权利金高 → 稳定 ID |

跨股票 CC 的首个档内指标为 `(strike - spot) / spot`，不比较不同股票的绝对行权价。无有效现价时不能编造比例，需按适用缺失语义处理。稳定 ID 用于完全相同情况下的确定性顺序，ID 为市场与 OpenD 合约代码，按标准股票代码、合约代码升序比较。

### 4.4 展示与推荐

形成美股 CSP、美股 CC、港股 CSP、港股 CC 四个独立列表：

- 每只存在合格候选的股票先按标的内排序选出最佳合约，股票列表展示全部股票的最佳合约，不仅展示推荐前三名。
- 对各股票的代表合约按跨标的规则排序，每个列表取前三个作为模拟推荐；不足三个不凑数。
- 展开股票展示其他全部合格期限、行权价合约及标的内顺序，不只展示同一期限或单个行权价。
- 未入选推荐但仍有合格合约的股票保留结果和排序解释；无合格合约、未满足条件、待设置或数据不可用的股票展示相应原因，不混同为零收益。
- 结果包含每手净权利金、相应持有期收益、年化收益率、到期日、行权价、接货折价或上行空间以及解释；CSP 另展示所需担保现金，CC 明示现价市值收益率基数及覆盖假设。

## 5. 刷新、市场状态与失败处理（已确认）

支持手动刷新和定时刷新，定时间隔选项为：关闭、10 分钟、30 分钟、1 小时。两个市场共用间隔，分别判断开市、休市；自动刷新跳过休市市场，两边都休市时暂停。手动刷新共用同一任务；其在休市时的取数边界待细化，不据此承诺休市仍有实时行情。

| 场景 | 要求 |
| --- | --- |
| 定时到点 | 根据市场状态刷新适用市场 |
| 上一轮尚未结束 | 单轮不重入；本次触发跳过，不排队积累 |
| 进行中点击手动刷新 | 共用当前任务和进度，不启动重叠轮次 |
| 开始刷新 | 保留旧结果及其时间，同时显示刷新中 |
| 某市场成功 | 更新该市场结果及上次成功时间 |
| 某市场失败 | 保留该市场旧结果，明确旧数据、时间与失败原因；不抹掉另一市场的健康结果 |
| 系统睡眠 | 不执行刷新 |
| 系统唤醒且已到期 | 在满足市场等刷新条件时只补一次，不补跑所有错过的周期 |

每个市场独立展示状态与上次成功时间，不能让一个市场的成功掩盖另一个失败。失败或不完整结果不作为推荐变化通知的输入；部分数据如何用于页面展示及何时认定一轮完整，列为待细化事项。

## 6. 窗口、菜单栏与系统生命周期（已确认）

- 关闭窗口后 App 留在菜单栏，继续按刷新规则运行；首次关窗提醒用户这一行为。
- 菜单栏提供：打开窗口、立即刷新 / 当前进度、刷新间隔、上次成功时间、连接状态和退出。市场状态与时间可分别辨认。
- 退出 App 停止 App 自有任务，不停止用户的 OpenD。
- 开机启动默认关闭，用户可主动开启。

## 7. 通知（已确认，部分基线细节待细化）

默认仅更新界面，不发送通知。提供两个独立开关：“推荐前三变化”“连接异常”。仅在用户开启通知时申请系统通知权限，不在首次启动时无条件申请。

### 推荐变化

- 四个市场策略列表分别建立和比较基线。
- 首次成功得到完整结果仅建立基线，不通知。
- 推荐合约身份、顺序或数量变化才通知；仅价格、净权利金或收益率数值变化不通知。
- 失败或不完整结果不能伪装成推荐数量减少或清空，不触发推荐变化通知。
- 通知点击后进入对应的市场与策略页面。

### 连接异常

- 同一故障只提醒一次，避免每次刷新重复打扰。
- 连接恢复后再次发生故障，可以再次提醒。
- 点击通知打开对应连接状态页面。

用户修改关注列表、策略开关、参数、通知设置后如何重建基线，以及何种事件构成同一故障、权限被拒后的交互，仍需细化；不把这些细节默认为已确认行为。

## 8. 券商插件、OpenD 与费用（已确认）

首期富途 / moomoo 接入实现为 App 内部随包插件。插件划分用于承载券商接入与费用适配，不引入插件商店或其他软件的插件协议。

用户负责官方 OpenD 的安装、登录、运行及升级；App 只做引导、连接状态和行情权限检查，默认本机连接且端口可调。不内置、下载、启动或停止 OpenD，不收取券商登录凭据。

费用按适用 OM 规则计算，由项目维护者维护，随券商插件或 App 发布更新，不实时抓取费率，用户不可修改。收益计算、筛选和排序必须使用同一套费用模型。结果提示：“手续费为估算，以实际账户收费为准。”

不同地区富途 / moomoo 费率的适配范围及差异需要核验；在完成之前不能宣称一个费用模型适用于所有地区和账户。

## 9. 本地保存与重新打开（已确认）

自动保存以下内容：关注股票、每股票策略开关、接货价、行权价及 DTE 范围、高级策略参数、刷新与通知偏好、最近结果及其时间。不保存 CC 持仓成本，不做云同步。

重新打开 App 时，先展示带时间的历史结果，让用户能识别数据的新旧。只有自动刷新已开启、相应市场开市且已到刷新时间时，才触发自动刷新；不因启动就无条件刷新。使用 Codable JSON 原子保存配置、最近结果及通知基线；配置改变后对应市场的下一次完整结果重建通知基线。

## 10. 技术栈（已确认并实施）

**采用全 Swift 技术栈。** SwiftUI 构建原生 Mac 窗口、菜单栏及系统交互界面；Swift 实现策略计算、费用逻辑与券商接入。不引入 Python 运行时或 Python 子进程，也不随包打包 Python。

这一决策统一 App 的实现语言与运行环境。策略移植仍需维护与 OM 的计算一致性，券商接入仍需验证 OpenD 的具体接口与兼容性；这些是已选技术路线的实现前核验事项，不代表语言选型未定，接入成功必须由实连证据确认，本轮美股验证已完成。

以下是实现及持续验证目标；用户已授权完成一期并提供已登录 OpenD，实际证据见第 13 节：

1. 核验 OpenD 的 Swift / 协议接入方式与兼容性，验证 Swift 连接用户自装 OpenD，并确认必要行情字段完整，包括真实合约乘数以及策略计算所需数据。当前已实现本机 TCP / JSON 适配与离线假服务测试；已完成 OpenD 10.11 美股实连及完整扫描，港股开市 / 不同地区权限需继续核验。
2. 用固定相同输入对照 Swift 与 OM 的计算、费用、筛选和排序；明确排除已批准的模拟输入、CC 不使用成本且按现价市值计算收益率、去掉成本门槛、真实账户容量资格及集中度等差异，其余差异须解释。已完成四组 OM 固定计算向量及关键规则边界测试，覆盖范围见 STRATEGY。

本地保存、后台调度、通知和开机启动采用系统能力，避免为首期引入不必要框架。本地存储已采用 JSON；最低 macOS 的兼容性和正式签名分发方案仍待核验，不改变 App 退出即停止自有任务的产品边界。

当前工程使用 SwiftUI 原生页面、Codable JSON 本地配置文件和无外部依赖的 Swift 协议实现；临时编译目标为 macOS 14 / arm64，不表示正式最低系统或分发方案已最终确定。已实现策略与费用引擎、系统后台生命周期、菜单栏和 Unix socket Agent 入口；未做公证分发。
